# Road to 0.1.1.0 — Steam Library Integration

## Selected release scope

The selected **four-part v0.1.1.0** release is shared ZIP-installer Steam library
integration. Prefer installed original entries where an explicit backend contract
supports it; preserve non-Steam installation. Never rewrite original game files.
Use automatic live-client Launch Options injection, exact backups, verified
restoration and reversible records. Manual launch-option entry is not a fallback.
Include post-extraction size/SHA-256 asset comparison, backend asset allowlists,
symlink-only deduplication confined to the converted package, read-only launch
isolation, recoverable manifests and asset restoration. See the
[deduplication acceptance gates](../steam-asset-deduplication.md); no backend
advertised safe before Frame gameplay/write-safety verification.

The original game must be installed through Steam **on this Frame** before
linking. Discover secondary mounted libraries, offer Steam's official install
flow when missing, and allow rescanning the same extracted package.

See [candidate notes](0.1.1.0.md) and the
[backend matrix and mandatory acceptance checklist](../steam-library-integration.md).
No final release or public tag before mandatory acceptance is verified.

## Objective and scope

Make the published 0.1.0 application easier to diagnose, reproduce and use, while
preserving the games and workflows already confirmed working. Add a single local
installation workflow to the Linux ARM64 app on Frame: preparation, any required
native compilation, dependency verification and Steam registration happen in one
operation. Offer direct patching of a selected Steam installation with reliable
backups/restoration, alongside the existing portable ZIP export. Prioritize defects
reported against the actual release archives. Keep new engines, SMAPI and major
runtime migrations outside this patch release.

Do not raise the version in main or retag 0.1.0 merely to record this plan. Keep
0.1.0 immutable. When implementation starts, use a development version for 0.1.1
and ship 0.1.1 only after both final archives and their checks pass.

## Proposed work packages

### Local installation and direct patching on Frame

This is a first-class 0.1.1 goal for the Linux ARM64 application. Windows retains
the existing prepare-and-transfer workflow. Running on Frame does not require
the user-facing two-stage process: the app should coordinate the existing stages
locally under one **Convert / Install** operation. Preparation, compilation,
validation and registration remain internal progress phases.

For STS2, reuse the existing preparation and device-side finishing implementation.
Run local toolchain/dependency preflight before changing an installation. The FMOD
SDK remains user-supplied and validated; local execution does not remove licensing
or build-tool requirements. Detect native ARM64 execution explicitly rather than
assuming that every Linux host can produce the Frame runtime.

Inspect the installed distribution as well as the game version. Steam may supply
a Linux x64 build rather than the Windows build accepted by an existing recipe.
Only enable local installation when that source variant has a supported profile;
do not bypass source hashes or silently apply a Windows-only preparation recipe.

The Linux app should offer two output modes:

- **Patch installed game:** select a supported Steam installation, prepare the
  native runtime/compatibility changes locally, validate them, back up affected
  files/settings, activate the patch and configure launching through Steam.
- **Create portable ZIP:** retain the existing export workflow for copying games
  to another device or keeping a portable package.

Direct patching must be explicit. Prepare in a separate staging area and validate
before activation. Track original and installed hashes, runtime/profile versions,
affected files, Steam launch settings and transaction state in a patch manifest.
Preserve assets, saves, user configuration and unrelated mods. Check writable
paths and available space before starting. Offer **Restore original installation**
and use a transaction/recovery journal for failed or interrupted activation.

Steam updates and Verify Files may replace patched files. Detect changed source
identities, invalidate incompatible patch state and re-inspect before reapplying.
Restoration must detect conflicts with newer Steam/user files and avoid blindly
overwriting them with an old backup. Do not silently overwrite existing launch
options or activate a recipe against a different game version.

Expose phase progress and actionable errors in the same GUI. Preserve validated
intermediate artifacts so a failed compilation/installation phase can retry
without repeating successful preparation. Cancellation must stop the owned
processes safely and leave either the original installation or a recoverable
transaction; it must not claim the game is ready before verification succeeds.

Implement direct patching through a shared install/restore contract, starting with
one already-supported backend, then apply it to other suitable backends. For
STS2, the local path must include required native compilation. Do not assume all
engines can use the same file replacement or Steam launch configuration.

Acceptance requires the actual frozen Linux ARM64 GUI on Frame: one-operation
STS2 installation; Steam launch/input and save/relaunch verification; a direct
patch/install/restore cycle for the initial backend; interrupted-phase recovery;
update/Verify Files handling; and regression of portable ZIP export and the
Windows transfer path. These are planned checks, not tests already performed.

### 1. Establish the release feedback baseline

Collect reports against 0.1.0 before choosing speculative fixes. Record:

- Application version, `BUILD.json` commit, host OS and archive checksum.
- Original game version, detected engine and selected runtime/profile.
- Whether the failure occurs during inspection, download, preparation, packaging,
  extraction, Steam installation, startup, input or gameplay.
- Whether a matching runtime was already cached and whether a required vendor SDK
  was supplied. Include errors and minimal reproduction steps.

Start from a shortlist of representative cases rather than rerunning every title
for every small edit. Choose additional tests based on the files and behavior each
fix changes. Keep startup-only and user-reported gameplay evidence distinct.

### 2. Provide a small diagnostics path

Review the reusable wrapper in preserved PR #18. Extract useful functionality
into the current launcher/package contract rather than merging old router or
README implementations wholesale. The proposed report should include runtime
identity, architecture, graphical environment availability, required library
checks, exit status and a log location.

Keep normal launching quiet. Provide an explicit diagnostic mode that preserves
the same Steam context, graphics environment and save/config directory as normal
launching. Avoid the earlier Stardew manual-test pattern that forced unrelated
Steam environment IDs or used a missing configuration directory.

Do not collect API tokens, complete environment dumps, proprietary game files,
save contents or private SDKs in support bundles. Do not silently upload reports.
Log generation must remain usable without SSH.

### 3. Finish artwork source identity

[Issue #32](https://github.com/tovakai/multi-engine-game-conversion-framework-by-tovakai/issues/32)
is the clearest remaining shared-flow feature gap. Audit the current source
identity helpers and their artwork callers before assuming every backend already
carries the original manifest identity through conversion.

Resolve identity once during source preparation, retain its provenance in the
inspection/build metadata, and use it for optional artwork lookup. Add cases for
normal Steam sources, archives without a manifest, conflicting sidecars and
non-Steam sources. Artwork/network failure must not prevent game conversion.

### 4. Consolidate the compatibility record

The existing report lists many working packages but lacks exact versions and
depth for some entries. Keep those reports; supplement them rather than treating
them as certified full-game tests. Add a consistent record with game/source
version, runtime recipe, converter commit, device, install method, tested input,
save/load and limitations.

Recommended release regression sample:

| Path | Representative check |
| --- | --- |
| Ren'Py 7 and 8 | One supported case per generation; preserve compiled-only data and test save/relaunch |
| Legacy Ren'Py migration | One guarded migration, with source-preservation and consent/cancellation checks |
| RPG Maker RGSS and MV/MZ | Existing working cases across the native runner and NW.js paths |
| GodotSteam | Brotato as the established baseline; separate startup/input/rendering claims for other candidates |
| GameMaker | Undertale conversion, controller input and save/load regression |
| LOVE / AGS / Construct | A previously reported working case for each affected path |
| MonoFrame | Pinned Stardew source, automatic provisioning, Steam-launched input and save/load |
| Licensed SDK gates | Missing/wrong-architecture SDK rejected; valid user-supplied dependency packaged correctly |

The matrix is a proposed target. Obtain exact source versions and availability
before choosing the final titles; do not claim tests were performed because the
table names a candidate. STS2's existing conversion logic is reused for the new
local Linux installation goal. Supporting new STS2 versions or otherwise expanding
that backend remains outside this patch release.

### 5. Triage the known game-specific issues

| Reported issue | 0.1.1 treatment |
| --- | --- |
| Cassette Beasts controller/rendering problems | Reproduce through the normal Steam package; separate input mapping from rendering/runtime behavior. A bounded shared fix may fit; renderer redesign does not |
| Cook, Serve, Delicious! 3 performance/controller problems | Measure and distinguish runner limitations from launch/mapping issues; do not promise an optimization before evidence |
| Desert Child graphical glitches | Record the renderer/runner issue and exact version; consider only a tested bounded fix |
| The Cat Lady controller recognition | Establish expected game controls and Steam mapping before labeling it a converter defect |
| Broken Sky / Live2D | Recheck ordinary archive extraction and SDK gating if a release report reproduces a failure; preserve the user-supplied licensing model |

These investigations are optional patch-release candidates, not reasons to delay
a useful maintenance release indefinitely. Ship a smaller verified fix set if
the larger problems require upstream engine work.

## Sequence and release gates

1. Triage public release feedback and choose the reproducible P0 fixes.
2. Define the shared local install/restore contract and implement one-operation
   STS2 installation plus the first direct-patching backend on Linux ARM64.
3. Implement the selected fixes and the minimal diagnostics/artwork work that is ready.
4. Run targeted regressions, then the Windows/Linux suite and both frozen builds.
5. Exercise local installation/patch/restore and affected game conversions through
   the frozen GUI from a clean cache,
   verify backups/restoration or unchanged export sources and archive contents,
   and perform the corresponding hardware
   checks through Steam. Record actual results and remaining limits.
6. Prepare 0.1.1 notes around the final fix set, promote through a reviewed PR,
   tag the exact release commit, verify both tagged artifacts and publish.

Required at release: no regression in the chosen baseline; actionable errors;
passing automated/build checks; exact artifact provenance and hashes; validated
changed gameplay/input/save behavior where claimed; no redistributable-assets
mistakes; and documentation matching the delivered behavior. Optional research
must not be described as implemented or block a verified maintenance release.

Use the [release procedure](../release-process.md) and the
[0.1.0 scope](0.1.0.md) as the baseline. This plan has no calendar promise until
the initial release-feedback triage establishes the work size.
